AI-Powered Web QA Automation

A course that teaches QA engineers to put generative AI into web test automation with an open stack, and to treat the model as a fast junior whose work a person must check. I rebuilt the syllabus from practitioner interviews, set up a production system for three authors, and restructured their drafts into short lessons of three kinds.

My role: Lead Learning Experience Designer. I owned the course design and the production process from the first interview to the edited lesson.

In short

The first syllabus followed vendor vocabulary: self-healing, visual AI libraries, predictive analytics. I interviewed three senior automation engineers, rebuilt five modules around their daily work, and set up a three-step authoring process so they could write in parallel. Their long drafts became 82 short lessons in three layers: theory, tool walkthrough, practice on one sandbox. A workshop built for a client team scored 9.1 of 10.

Key decision 1 · Syllabus

A syllabus rebuilt around what practitioners do every day

The first syllabus followed the market's vocabulary: self-healing tests, visual AI libraries, predictive analytics. I interviewed three senior automation engineers and compared each module with their daily work. Two modules changed their premise and one was replaced.

One principle across all modules

Human-in-the-loop moved from a single lesson to a rule every module must apply: each AI output has a validation step.

Outcomes without marketing

"Reduce maintenance time by a measurable percentage" became evaluate, configure, validate, compare. The effect depends on the team, so the promise had to go.

No vendor lock-in

An open stack and model APIs instead of paid platforms, on an expert's warning about cost.

Original moduleWhat experts saidWhat it became
AI fundamentals as broad theoryTheir concern is data security and cost. Nobody mentioned the value of general theory.Prompting for QA tasks, masking personal data, mock data, token cost and when not to use AI
Self-healing test scriptsOpinions split. Two of three said self-healing hides real bugs.Locator generation, and auto-fixing with a hard retry limit: one attempt, then a bug ticket

I kept the reasoning as a table: original syllabus, what we change, what replaces it, and why according to the interviews. 24 rows. It served as the brief for all three authors.

Key decision 2 · Authoring system

A production system for three experts who had never written a course

Three practitioners wrote five modules at the same time. Without rules they would repeat setup lessons, contradict each other and deliver long articles. I wrote a guide with one process rule: architecture before text.

Step 1 · approval gate

Lesson-by-lesson plan

Start from the module's final task and work backwards: what must the learner know and do to reach it? Each answer becomes one lesson.

Output: a table of lessons with type and goal

Step 2 · approval gate

Cross-cutting project

One project per module, spread across the practice lessons. Every practice lesson adds a working block.

Output: baseline, process and result for each stage

Step 3

Lesson writing

Templates for theory lessons, practice lessons and knowledge checks, with examples.

Output: lessons in platform format

Rules for parallel work

  • Boundaries. Each expert owns named modules. Universal basics live in Module 1 only.
  • No repeated setup. Assume the core stack works from Module 2 on.
  • Chapter logic. The first chapter of a module explains why. Later chapters show how: manual first, then automated.
  • Atomicity. One lesson, one small win.
  • Bridge to the workshop. Independent practice teaches each tool separately before the live session combines them.

One-to-one sessions with a question list

Before each session I read the draft against the brief and prepared questions per lesson block, in two languages. Typical ones:

  • Where do these figures come from: your experience, a benchmark, one team? It decides how the lesson presents them.
  • This rule appears as a footnote. The brief needs it as an explicit teaching moment. How often does the case occur?
  • Why is the threshold three to four corrections? What happens if you edit line by line?

The answers turned rules of thumb into explained conclusions in the lesson text.

Key decision 3 · Lesson structure

Long expert articles cut into three kinds of short lesson

The first drafts were accurate and very long. One lesson could explain a concept, demonstrate a tool and set a task. Learners could not tell what a lesson wanted from them. With the design team I worked out a three-layer structure and rebuilt the whole course on it.

Theory layer · 31 lessons

Why

A concept and the judgment behind it.

"I can explain why…"
"I can distinguish…"

Tool walkthrough · 18 lessons

How

One procedure in one tool, shown step by step.

"I know how to…"

Domain practice · 30 lessons

Do

The same skill applied to the course's sandbox shop.

"I can … in the context of…"

Before · one chapter

Data fluency for QA

  • Three long lessons
  • Statistics, tool report and exercise mixed in each
  • Objectives as a topic list
→
After · the same chapter

Seven lessons in sequence

  • Why the 95th percentile beats the average theory
  • Reading a performance report walkthrough
  • Annotated report: guided reading practice
  • Then the same cycle for failure metrics and percentiles

The objective names the layer

Each lesson has an "I can" statement whose verb shows the layer. The learner knows whether to understand, follow or produce.

One sandbox through the course

Every practice lesson uses the same demo shop: its locators, its CI logs, its checkout bug. Context is learned once.

Practice with a known answer

Tasks such as "classify diffs against ground truth" or "audit a flawed pipeline" let the learner check themselves.

Key decision 4 · Workshops

Workshops as the next step after practice, and built for the client's team

I separated two tracks from the start. Independent practice covers one tool or script at a time. A 90-minute workshop combines them into an integration that needs an expert in the room.

ModuleIndependent practiceLive workshop
Security and fundamentalsA filter that masks personal data and a token cost calculatorA secure generator of test data from a real file, with output validation
Locators and auto-fixingReliable locators on a page with a poor, dynamic structureA CI workflow that fixes a locator once and files a bug if the fix fails
Bug triageAn AI reviewer for test pull requestsA bot that reads a long CI log and drafts a ticket with repro steps

Client workshop: Test Quality Guard Agent

A client's QA team asked for practice closer to their work than generic agent building. The workshop builds an agent that reads a test together with the code under test and returns a verdict.

PASS
WEAK
FAKE
  • A rubric of eleven criteria, applied by hand first and by the agent after
  • Three prompt stages, so learners see why each one is more reliable
  • Prepared test files with an answer key, in two languages of the client's stack
  • The rubric is a text file: the agent improves without code changes

Three roles for a mixed room

RoleWhoTask in the build block
ObserverJuniors, manual testersRun the agent on prepared files and compare with the answer key
BuilderMid-levelRun it on a test from their own repository and refine the rubric
ArchitectSeniorsTrace the code path and design an adapter for another language

Preparation is checked before the session: learners clone the repository and run one diagnostic command. Green means ready.

For a second client I designed two further workshops: AI-assisted test case generation, and building a QA agent from scratch.

Results

The highest-rated session of a four-track pilot, and a base for custom tracks

Workshop rating

Test Quality Guard Agent: value 9.1 and likelihood to recommend 8.9 of 10. Eight responses, the best result among the four tracks of the client's pilot.

Requirements fed back

The pilot's QA group asked for QA-specific practice and ready connectors instead of "write your own". Both went into the next track for that client.

Reuse

Lessons from this course and from my mobile QA course were combined into custom web and backend QA tracks for two companies, launched in November 2026.

The custom tracks had just started at the time of writing, so completion data is not available yet.
